> 适用于单机部署的 NIP（Linux 内核抓包）平台，涵盖回铃检测、实时通话内容质检、HEP 传输、CDR 生成、录音备份及 PostgreSQL 数据库等全业务场景。
>
> 原则是：主频尽量高、内存容量高、网卡吞吐高、SSD 存储性能高、录音磁盘 I/O 稳定
>
> 网络配置原则：尽可能无NAT,网卡PPS 稳定，避免多层包情况下出现丢包、延迟包。
>

---

## 一、概述

NIP 平台基于 Linux 内核抓包技术，单机部署即可承载以下核心业务：

- **回铃检测**：实时解析信令与媒体状态
- **实时通话内容质检**：媒体流解析、转码与特征提取
- **HEP 传输**：信令抓取与转发
- **CDR 生成**：会话状态维护与结构化数据写入
- **录音备份**：持续写入媒体数据
- **PostgreSQL 数据库**：存储 CDR、质检结果、会话状态等结构化数据

硬件选型应围绕 **并发能力、CPU 处理能力、内存容量、网卡吞吐与稳定性、SSD 数据库存储性能、录音磁盘 I/O 能力** 进行综合设计，避免在高峰话务下出现丢包、延迟、质检滞后、数据库瓶颈或录音缺失。

---

## 二、业务功能与硬件需求对照

| 功能 | 对硬件的主要要求 |
|---|---|
| 回铃检测 | 实时解析信令与媒体状态，要求 CPU 处理稳定 |
| 实时通话内容质检 | 媒体流解析、转码或特征提取，CPU 和内存压力较高 |
| HEP 传输 | 信令抓取与转发，要求网卡稳定、低丢包 |
| CDR 生成 | 会话状态维护，写入 PostgreSQL，要求 CPU、内存与磁盘 I/O 稳定 |
| 录音备份 | 持续写入媒体数据，要求磁盘 I/O 和存储容量充足 |
| PostgreSQL 数据库 | 存储 CDR、质检结果、会话状态等结构化数据，要求 SSD 高 IOPS、低延迟 |

---

## 三、网卡选型要求：必须支持 Intel I350

NIP 抓包场景对网卡稳定性要求极高，网卡必须具备长期满负载运行能力，并能够稳定接收 SIP/RTP、信令、媒体流及 HEP 数据。

### 3.1 网卡基本要求

| 项目 | 要求 |
|---|---|
| 网卡芯片 | **必须支持 Intel I350 系列** |
| 推荐型号 | Intel I350-T2、I350-T4、I350-AM2、I350-AM4 等 |
| 接口类型 | PCIe 2.0 x4 及以上兼容插槽 |
| 端口数量 | 建议至少双端口，推荐四端口 |
| 网络类型 | 千兆以太网 |
| 传输介质 | RJ45 或 SFP/光纤，根据现场网络环境选择 |

### 3.2 网卡功能要求

- **支持 Jumbo Frame**：提升大包传输效率，减少小包处理压力
- **支持 VLAN 标记**：便于对接带 VLAN 的交换网络
- **支持中断调节**：降低高并发抓包时的 CPU 中断压力
- **支持链路聚合/Teaming**：可用于管理网、抓包网、HEP 传输网分离或带宽聚合
- **支持多端口隔离**：便于将 SIP 信令、RTP 媒体、HEP 传输、管理流量分开
- **Linux 驱动兼容**：需确认目标 Linux 内核版本支持 I350 驱动

### 3.3 网卡端口规划建议

建议采用四端口 I350 网卡，典型用途如下：

| 端口 | 建议用途 |
|---|---|
| 端口 1 | 管理口，用于 SSH、监控、系统维护 |
| 端口 2 | SIP 信令抓包口 |
| 端口 3 | RTP 媒体抓包口 |
| 端口 4 | HEP 传输或录音备份传输口 |

> 如果现场只有双端口 I350 网卡，可采用双网卡组合：1 张 I350-T2 用于管理口和 HEP 传输口，1 张 I350-T4 用于 SIP/RTP 抓包口和备份传输口。

## 四、CPU 选型与并发能力

根据当前单机性能基线，NIP 平台可按以下 CPU 能力进行选型：

| 服务器配置 | 支持并发 | 适用场景 |
|---|---:|---|
| Intel Xeon E5-2680 | **2000 并发** | 中小型话务、常规质检、标准录音备份 |
| Intel Xeon 6183，96GB 内存 | **5000 并发** | 中大型话务、实时质检、HEP 传输、录音备份 |

### 4.1 E5-2680 方案：2000 并发

适合中小型 NIP 部署场景，适用条件包括：

- 单点部署，话务并发不超过 2000
- 实时质检规则复杂度中等
- 录音备份压力可控，HEP 传输量适中

### 4.2 6183 + 96GB 内存方案：5000 并发

适合中大型 NIP 部署场景，适用条件包括：

- 高并发话务，实时通话内容质检
- 回铃检测与 CDR 并行处理
- HEP 传输压力较大，录音备份数据量较高

## 五、PostgreSQL 数据库 SSD 存储要求

PostgreSQL 是 NIP 平台中存储 CDR、质检结果、会话状态等结构化数据的核心组件。**必须使用 SSD**，NVMe SSD 为高性能首选，机械硬盘（HDD）仅适用于冷数据归档。

### 5.1 为什么 PostgreSQL 必须使用 SSD

- **随机 I/O 密集**：PostgreSQL 的查询、索引扫描、WAL 写入等操作以随机读写为主，SSD 的随机 IOPS 是 HDD 的 10～20 倍
- **WAL 日志延迟敏感**：WAL（预写日志）刷盘对延迟极为敏感，使用 HDD 会导致事务提交延迟增大，高并发下可能引发连接堆积
- **高并发写入场景 IOPS 优先**：NIP 平台在高并发话务下，CDR 写入和质检结果写入会产生大量并发 I/O，SSD 的高 IOPS 能力是保障系统稳定的关键

### 5.2 SSD 类型选择

| SSD 类型 | 适用场景 | 性能参考 |
|---|---|---|
| NVMe SSD | PostgreSQL 数据盘、WAL 盘（**推荐**） | IOPS 可达 100K～1M+，延迟 < 0.1ms |
| SATA SSD | 预算有限时的替代方案 | IOPS 约 100K，延迟约 0.1ms |
| HDD | 仅用于冷数据归档，**不推荐用于数据库** | IOPS 约 100～200，延迟 5～10ms |

> **建议**：PostgreSQL 数据盘和 WAL 盘优先选用企业级 NVMe SSD，DWPD（每日全盘写入次数）应 ≥ 1，确保长期写入耐久性。

### 5.3 存储布局规划

PostgreSQL 的存储布局应将数据文件、WAL 日志、操作系统分离到不同物理设备，避免 I/O 争用：

| 存储组件 | 挂载建议 | 说明 |
|---|---|---|
| 操作系统 | 独立 SSD | 系统盘，480GB 及以上 |
| PostgreSQL 数据文件 | 独立 SSD/NVMe | 存放表数据、索引等 |
| PostgreSQL WAL 日志 | 独立 NVMe SSD | 延迟最敏感，建议单独挂载 |
| 录音数据 | 独立数据盘 | 与数据库盘物理隔离，避免 I/O 争用 |

### 5.4 容量与 RAID 建议

- PostgreSQL 数据盘需预留 **30%～50%** 的额外空间，用于 WAL 日志、临时文件及数据膨胀
- WAL 盘容量建议不低于数据盘容量的 25%
- 数据盘推荐 **RAID 10**，兼顾性能与冗余
- WAL 盘建议使用 **RAID 1** 或独立 NVMe SSD，确保写入延迟最低

### 方案一：2000 并发推荐配置

| 组件 | 推荐配置 |

## 七、内存选型建议

内存容量直接影响 NIP 抓包缓存、会话状态维护、质检缓冲、录音写入能力以及 PostgreSQL 数据库性能。

| 并发规模 | 内存建议 |
|---|---:|
| 2000 并发 | 64GB 及以上 |
| 5000 并发 | 96GB 及以上 |

**PostgreSQL 内存参数建议**：

- `shared_buffers`：建议设为系统内存的 25%，最大不超过 16GB
- `effective_cache_size`：建议设为系统内存的 50%～75%
- `work_mem`：根据并发连接数和查询复杂度调整，建议 4～16MB
- `maintenance_work_mem`：建议设为系统内存的 5%～10%，最大不超过 2GB

> 优先使用服务器 ECC 内存，尽量按内存通道均衡插满，提高内存带宽。

## 八、系统优化建议

### 8.1 网卡优化

- 开启网卡多队列
- 合理绑定抓包口与管理口，避免 SIP/RTP 抓包口与管理流量混用
- 根据实际网络环境开启 Jumbo Frame
- 检查网卡中断调节参数，避免高并发时 CPU 中断过高

### 8.2 CPU 优化

- 确认 NIP 进程可调度到足够多的 CPU 核心
- 避免将抓包、质检、录音写入全部绑定到同一核心
- 如果系统支持 CPU 亲和性，可将抓包线程与业务处理线程合理分离

### 8.3 磁盘与 PostgreSQL 优化

- 录音目录和 PostgreSQL 数据目录使用独立磁盘或独立分区，避免 I/O 争用
- 文件系统推荐使用 XFS 或 ext4，挂载时添加 `noatime` 属性以提升 I/O 性能
- SSD 场景下，`random_page_cost` 建议设为 1.1～1.5，`effective_io_concurrency` 建议设为 200
- 定期检查磁盘使用率、I/O 延迟和写入错误

## 十、最终选型建议

如果业务并发稳定在 **2000 以内**，建议选择：

- **E5-2680 服务器** + **64GB 及以上内存**
- **Intel I350-T4 四端口千兆网卡**
- **企业级 SSD 系统盘**
- **企业级 SSD（NVMe 优先）作为 PostgreSQL 数据盘 + 独立 WAL 盘**
- **独立数据盘用于录音存储**

如果业务并发需要达到 **5000**，建议选择：

- **6183 服务器** + **96GB 及以上内存**
- **Intel I350 系列四端口网卡，必要时双网卡组合**
- **企业级 SSD 系统盘**
- **企业级 NVMe SSD 作为 PostgreSQL 数据盘（RAID 10）+ 独立 NVMe WAL 盘**
- **高耐久数据盘或 RAID 存储用于录音备份**

> NIP 硬件选型应以 **Intel I350 网卡为基础网络能力，以 CPU 和内存决定并发上限，以 SSD 保障 PostgreSQL 数据库 I/O 性能，以独立存储保障录音备份可靠性**。实际部署前，建议结合 SIP/RTP 码率、录音格式、质检规则复杂度、HEP 传输频率、录音保留周期以及 PostgreSQL 数据增长预期进行最终容量评估。
