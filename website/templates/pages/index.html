核心能力

把复杂的 SIP 边界，收敛成一套组件

自研协议栈、真 B2BUA、媒体锚定与模块系统，共享一套代码和配置，覆盖企业分支、呼叫中心与运营商接入。

自研 SIP 协议栈

解析器、事务状态机与 B2BUA 环路全部用 C11 从零实现，不基于 PJSIP、Sofia-SIP 或 reSIProcate。

  • RFC 3261 / 3262 / 3264 / 3265
  • SIP over WebSocket（RFC 7118）
  • 可审计、可预测、可裁剪

真 B2BUA，不是代理

每通呼叫都在 NSBC 终止并重新发起，拓扑隐藏、DoS 防护与欺诈检测内置于信令层。

  • A / B 腿独立事务与对话
  • Via / Contact / Record-Route 改写
  • 会话定时器与 RFC 7989 Session-ID

媒体锚定 + DTLS-SRTP

OpenSSL 负责 DTLS-SRTP 密钥协商，libsrtp2 负责媒体加密，WebRTC 与 SIP 终端之间可自动选择中继。

  • Jitter Buffer、VAD、DTMF
  • T.38 Fax 透传
  • SRTP 与 RTP 双向中继

内置 PBX 与呼叫中心

拨号计划、IVR、语音信箱、ACD 队列与坐席池都是内置模块，与 SBC 共享同一套配置。

  • YAML 拨号计划与动作编排
  • 坐席池 + 技能队列
  • Ring Group、会议与呼叫控制

模块化，可裁剪

configure 期按调用图选择模块：核心模块静态链接，其余编译为 mod_*.so，启动时按 mod.load 清单加载。

  • --with-modules / --without-modules
  • 运行时 enable / disable
  • 自定义模块只需声明 NSBC_MOD()

可观测性开箱可用

Prometheus 指标、带 trace_id 的结构化日志、HEPv3 抓包，以及 Web 控制台的实时会话与 CDR。

  • CPS、并发、事务、RTP 指标
  • HEPv3 → Homer / sngrep
  • CDR 与录音集中查询
架构

C11 内核 + Rust 边车
职责清晰的两进程模型

nsbcd 是单二进制守护进程：Reactor 线程收包，Worker 池承载事务、媒体与 CDR， 信令与媒体在同一进程内完成锚定。管理面则是独立的 Rust 边车 nsbc-web， 通过 Unix Domain Socket 与内核通信。

  • C 核心零数据库依赖，故障域更小
  • 管理面唯一数据库层（SQLite / PostgreSQL / MySQL）
  • 配置热重载：SIGHUP 或 nsbc_cli config.reload
  • 与现有 PBX / SIP Trunk / 业务 API 平滑对接

呼叫流程

一通呼叫
在内部经历什么

从 401 质询到 CDR 落盘，每一步都在同一个进程内完成，链路可追踪、失败可复现。

  1. 鉴权与防护 — Digest 质询、黑白名单、速率限制与自动封禁。
  2. 拨号计划路由 — 按被叫号码、主叫号码与时段匹配规则。
  3. 注册查询 — Location DB 解析被叫 Contact，决定 A / B 腿。
  4. B 腿重建 INVITE — 改写 R-URI、Contact 与 SDP，完成拓扑隐藏。
  5. 媒体锚定 — DTLS-SRTP 协商、SRTP/RTP 中继或按策略直通。
  6. 结束与落账 — BYE 拆除、录音落盘、WAL 式 CDR 与事件推送。

Core Capabilities

Converging the complex SIP border into one component set

A homegrown protocol stack, true B2BUA, media anchoring and a modular system — sharing one codebase and one config, covering enterprise branches, contact centers and carrier interconnection.

Homegrown SIP Stack

Parser, transaction state machine and B2BUA loop are all implemented from scratch in C11 — no dependency on PJSIP, Sofia-SIP or reSIProcate.

  • RFC 3261 / 3262 / 3264 / 3265
  • SIP over WebSocket (RFC 7118)
  • Auditable, predictable, configurable

True B2BUA, Not a Proxy

Every call is terminated and re-originated inside NSBC. Topology hiding, DoS protection and fraud detection are built into the signaling layer.

  • Independent transactions and dialogs on A / B legs
  • Via / Contact / Record-Route rewriting
  • Session timer and RFC 7989 Session-ID

Media Anchoring + DTLS-SRTP

OpenSSL handles DTLS-SRTP key negotiation, libsrtp2 handles media encryption. WebRTC and SIP endpoints can automatically select relay.

  • Jitter Buffer, VAD, DTMF
  • T.38 Fax passthrough
  • Bidirectional SRTP / RTP relay

Built-in PBX & Call Center

Dial plan, IVR, voicemail, ACD queue and agent pool are all built-in modules, sharing one config with the SBC.

  • YAML dial plan + action orchestration
  • Agent pool + skill-based queues
  • Ring Group, conference and call control

Modular, Trim-able

Modules are selected by call graph at configure time: core modules are statically linked, the rest are compiled as mod_*.so and loaded from a mod.load manifest at startup.

  • --with-modules / --without-modules
  • Runtime enable / disable
  • Custom modules just declare NSBC_MOD()

Observability Out of the Box

Prometheus metrics, structured logs with trace_id, HEPv3 packet capture, and real-time sessions plus CDR in the web console.

  • CPS, concurrency, transaction, RTP metrics
  • HEPv3 → Homer / sngrep
  • Centralized CDR and recording queries
Architecture

C11 Core + Rust Sidecar
A clean two-process model

nsbcd is a single-binary daemon: Reactor threads receive packets, a Worker pool carries transactions, media and CDR — signaling and media are anchored in the same process. The control plane is a separate Rust sidecar nsbc-web, communicating with the core via Unix Domain Socket.

  • Zero DB dependency in the C core — smaller failure domain
  • The only DB layer lives in the control plane (SQLite / PostgreSQL / MySQL)
  • Hot reload: SIGHUP or nsbc_cli config.reload
  • Smooth integration with existing PBX / SIP Trunk / business APIs

Call Flow

What happens inside
during a call

From the 401 challenge to the CDR write — every step happens inside the same process. The path is traceable, failures are reproducible.

  1. Auth & Protection — Digest challenge, allow/deny lists, rate limiting and auto-ban.
  2. Dial Plan Routing — Match rules by called number, caller and time-of-day.
  3. Registration Lookup — Location DB resolves the callee Contact, decides A / B legs.
  4. Rebuild B-leg INVITE — Rewrite R-URI, Contact and SDP to complete topology hiding.
  5. Media Anchoring — DTLS-SRTP negotiation, SRTP/RTP relay or policy-driven bypass.
  6. Teardown & Billing — BYE teardown, recording flush, WAL-style CDR and event push.
