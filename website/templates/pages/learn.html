从一通电话开始，理解 SIP 与 SBC

不涉及代码，也不需要通信背景。读完这一页，你会知道电话是怎么"接通"的、声音是怎么"传过去"的，以及 SBC 为什么站在两者中间。

第一步

SIP 只负责"接通"，不负责"说话"

SIP（Session Initiation Protocol）是一套信令协议：它负责找到对方、协商能力、建立会话、在结束时拆除会话。 真正的声音和画面由另一条通道 RTP 承载。

可以把它类比成打电话前的"约定"：SIP 是双方确认"谁打给谁、用什么语言、在哪个端口说"的过程； RTP 才是随后真正的声音流。

一句话记忆：SIP 建立、修改、结束会话；RTP 传输媒体。两者走不同的端口，也常常走不同的网络路径。

基础概念

看懂 SIP，先认识这六个词

后面的呼叫流程与 SBC 行为，都建立在这些概念之上。

概念通俗解释在 NSBC 中的对应

Registrar（注册服务器）记录"某个号码当前在哪里"，即 Contact 地址registrar + Location DB
Proxy（代理）只转发信令，不终止会话，媒体通常不经过它路由与中继转发路径

Transaction（事务）一次请求与它所有响应构成的整体，有超时与重传事务层（sip_txn）
Dialog（对话）由 Call-ID、From tag、To tag 标识的一段持续会话对话管理（sip_dialog）
SDP会话描述：告诉对方"我支持什么编解码、请把媒体发到哪个 IP 和端口"SDP 解析、改写与过滤

请求与响应

请求包括 INVITE、ACK、BYE、CANCEL、REGISTER、OPTIONS；响应用三位数字表示结果。

  • 1xx：临时响应（100 Trying、180 Ringing）
  • 2xx：成功（200 OK）
  • 3xx–6xx：重定向、失败、超时、拒绝

注册与保活

终端启动后先 REGISTER，告诉服务器"我在这个地址"。注册有有效期，需要在过期前刷新。

  • 刷新时机通常是 Expires / 2
  • OPTIONS 可用于探测对端是否在线
  • 连续失败时需要重新注册

媒体协商

SDP 采用 Offer / Answer 模型：主叫列出能力，被叫从中选择并回复，双方取交集。

  • 编解码列表与优先级
  • 媒体 IP、端口与传输协议
  • 加密属性（RTP/SAVP、DTLS 指纹）
呼叫流程

一通电话的完整信令

下面是最典型的成功呼叫。主叫称为 UAC，被叫称为 UAS，中间的 SBC 会把一条信令拆成两段。

  1. INVITE — 主叫发起呼叫，携带 SDP offer，说明自己支持的编解码与接收地址。
  2. 100 Trying / 180 Ringing — 服务器确认收到请求；被叫开始振铃，主叫听到回铃音。
  3. 200 OK — 被叫接听，返回 SDP answer，双方编解码与端口就此确定。
  4. ACK — 主叫确认，会话正式建立，媒体开始传输。
  5. BYE — 任意一方挂断，另一方返回 200 OK，会话结束并生成 CDR。
SDP

"把声音发到哪里、用什么编码"，写在 SDP 里

SDP 是纯文本的会话描述，随 INVITE / 200 OK 一起传输。它不传媒体，只告诉双方媒体该怎么发。

  • c= 媒体连接地址：对方应把 RTP 发到这个 IP。
  • m= 媒体行：类型、端口、传输协议与 payload 列表。
  • a=rtpmap 把 payload 编号映射到具体编解码。
  • a=fmtp 编解码参数，例如 Opus 采样率、H.264 profile。
  • a=candidate / a=fingerprint ICE 候选与 DTLS 证书指纹，WebRTC 必需。
为什么经常"单通"？如果 SDP 里写的是内网地址（如 192.168.1.20），对端会把声音发进黑洞。SBC 的价值之一，就是把地址改写成公网可达的地址，并可选地中转媒体。 
v=0
o=1001 3582 3582 IN IP4 192.168.1.20
s=NSBC call
c=IN IP4 192.168.1.20
t=0 0
# 音频：端口 40000，RTP/AVP，payload 0 / 8 / 111
m=audio 40000 RTP/AVP 0 8 111
a=rtpmap:0   PCMU/8000
a=rtpmap:8   PCMA/8000
a=rtpmap:111 opus/48000/2
a=fmtp:111 maxplaybackrate=8000;useinbandfec=1
a=ptime:20
a=sendrecv

上面的 c= 是典型的内网地址 —— 未经 SBC 改写时，公网对端无法把媒体送回来。

为什么需要 SBC

企业网络与运营商之间，隔着五道坎

SBC（Session Border Controller）直译是"会话边界控制器"。它存在的理由，就是让两个互不信任、互不了解的网络能够安全地通话。

1. NAT 与地址不通

内网终端不知道自己的公网地址，SDP 里写的是私有 IP；防火墙还会随机映射端口。SBC 通过改写 SDP、对称 RTP 与端口预测，让媒体找到正确的路。

2. 安全与盗打

暴露在公网的 SIP 端口会持续被扫描、爆破与注册劫持。SBC 在这里做认证、限速、黑白名单与自动封禁，把攻击挡在业务之外。

3. 协议与编解码不兼容

不同厂商对头字段、SDP 顺序、会话定时器的实现差异很大。SBC 做协议规范化与能力裁剪，必要时启用转码，让两端"听得懂"。

4. 拓扑暴露

如果内网 PBX 直接对接外网，对方能看到你的服务器地址、端口与内部号码结构。B2BUA 把呼叫拆成两段，隐藏内部拓扑。

5. 计费、录音与合规

媒体经过 SBC，才能可靠地统计丢包、抖动、MOS，完成录音、CDR 与审计。直通模式下这些数据会丢失。

没有 SBC 时会发生什么

  • 呼叫能振铃，但接通后无声
  • 内网服务器地址被外部扫描到
  • 不同厂商设备"信令通、媒体不通"
  • 被爆破后产生高额国际长途
  • 出问题只能靠两端各查一半日志
一句话总结：SBC 不是"可选的加速器"，而是公网 SIP 部署的边界基础设施 —— 它同时承担安全网关、协议翻译、媒体代理与观测点的角色。
工作原理

SBC 内部到底做了什么

把 SBC 想成一条流水线：每个 INVITE 进来，都要依次经过鉴权、路由、改写、媒体与落账。

  1. 信令防火墙 — 校验格式与来源，限制速率，拦截畸形请求与扫描。
  2. 认证 — 用 Digest 质询确认身份，必要时查询注册库中的 HA1。
  3. 路由 — 按被叫号码、主叫、时间段匹配拨号计划，决定去往哪个分机或中继。
  4. B2BUA 拆腿 — 主叫侧一条腿、被叫侧一条腿，各自维护事务与对话。
  5. 改写与协商 — 改写 R-URI、Via、Contact 与 SDP，裁剪编解码，处理 NAT。
  6. 媒体与落账 — 按策略中继或直通，采集 RTP 统计，结束写 CDR、停录音。

对应到 NSBC

信令与媒体在同一守护进程内完成，边界行为可在一处配置：

  • security：黑白名单、限速、自动封禁
  • registrar / Location DB：注册与寻址
  • dialplan：路由与号码改写
  • signaling：B2BUA 两腿与 SDP 处理
  • media_bridge：RTP / DTLS-SRTP 中继
  • billing / recording：CDR 与录音
媒体路径

中继还是直通？两种取舍

SBC 支持让媒体经过自己（relay），也支持只改信令让媒体直通（bypass）。选择哪一种，取决于你是否需要看见媒体。

WebRTC

浏览器为什么更需要 SBC

WebRTC 把安全要求写进了协议：媒体必须加密，地址必须经 ICE 协商，证书指纹必须随 SDP 传递。传统 SIP 终端并不具备这些能力。

  • 传输不同 — 浏览器通过 WSS 承载 SIP，而不是 UDP 5060。
  • 媒体不同 — WebRTC 强制 SRTP，密钥由 DTLS 协商。
  • 编解码不同 — 浏览器偏爱 Opus / VP8 / H.264，PSTN 侧通常是 G.711。
  • 网络不同 — 需要 ICE、STUN、TURN 处理 NAT 与防火墙。

SBC 在这里不只是"边界"，还是翻译器：把 WSS 还原成 SIP，把 DTLS-SRTP 转成普通 RTP/SRTP，按需转码，让浏览器与话机、运营商互通。

常见误区

几个容易混淆的问题

SBC 就是防火墙吗？

不是。防火墙按 IP 与端口放行，SBC 理解 SIP 语义：它能识别一次注册是否合法、一通呼叫该路由到哪里、SDP 里的地址是否需要改写。两者通常配合使用。

有了 PBX 还需要 SBC 吗？

如果 PBX 只服务内网，可以不需要；一旦要对接公网、运营商中继或 WebRTC，就需要 SBC 处理安全、NAT 与互通。NSBC 把两者做进了同一套系统，但仍可按需只启用边界能力。

为什么"能振铃但没声音"？

信令通了只说明 SIP 路径正常；没声音通常是 SDP 地址不可达、RTP 端口被拦、编解码无交集，或媒体路径没经过可用的中继。

SIP 一定是明文吗？

不是。SIP 可以跑在 TLS 上（SIPS，默认 5061），WebRTC 场景走 WSS。媒体侧则用 SRTP 或 DTLS-SRTP 加密。

注册成功就代表能打电话？

不代表。注册只说明终端与注册服务器可达；真正呼叫还依赖路由规则、被叫在线状态、媒体协商与防火墙放行。

媒体直通一定更好吗？

直通延迟更低、更省资源，但失去媒体可见性，也无法录音与转码。公网与 WebRTC 场景通常应选择中继。

Understanding SIP & SBC, starting from one call

No code, no comms background required. After reading this page you'll understand how a call is "connected", how the voice gets "through", and why an SBC sits between them.

First Step

SIP only "connects", it never "speaks"

SIP (Session Initiation Protocol) is a signaling protocol: it finds the peer, negotiates capabilities, establishes the session, and tears it down when done. The actual audio and video are carried on a different channel: RTP.

Think of it as the "agreement" before a phone call: SIP is the two parties confirming who calls whom, which language to use, and on which port to speak. RTP is the voice stream itself that follows.

One-line memory: SIP creates, modifies and ends sessions; RTP transports media. They use different ports and often take different network paths.

SIP vs RTP — the division of labor

Requests & Responses

Requests include INVITE, ACK, BYE, CANCEL, REGISTER, OPTIONS. Responses use three-digit codes.

  • 1xx: provisional (100 Trying, 180 Ringing)
  • 2xx: success (200 OK)
  • 3xx–6xx: redirect, failure, timeout, rejection

Registration & Keepalive

After boot, a terminal sends REGISTER to tell the server "I'm at this address". Registrations have lifetimes and must be refreshed before they expire.

  • Refresh timing is typically Expires / 2
  • OPTIONS can probe whether a peer is alive
  • Re-register when consecutive refreshes fail

Media Negotiation

SDP uses an Offer / Answer model: caller lists capabilities, callee picks from them and replies; both sides take the intersection.

  • Codec list and priorities
  • Media IP, port and transport protocol
  • Encryption attributes (RTP/SAVP, DTLS fingerprint)
Call Flow

The full signaling of one phone call

Below is the most typical successful call. The caller is UAC, the callee is UAS, and the SBC in the middle splits one piece of signaling into two.

  1. INVITE — Caller originates, carries an SDP offer stating supported codecs and receiving address.
  2. 100 Trying / 180 Ringing — Server acknowledges receipt; callee starts ringing, caller hears ringback.
  3. 200 OK — Callee picks up, returns an SDP answer. Codecs and ports are now locked on both sides.
  4. ACK — Caller confirms, the session is formally established and media starts flowing.
  5. BYE — Either side hangs up; the other returns 200 OK. Session ends and a CDR is generated.
SDP

"Where to send voice, and which codec to use" — written in SDP

SDP is a plain-text session description that travels alongside INVITE / 200 OK. It doesn't carry media; it tells both sides how media should be sent.

  • c= Media connection address: the peer should send RTP to this IP.
  • m= Media line: type, port, transport protocol and payload list.
  • a=rtpmap Maps a payload number to a specific codec.
  • a=fmtp Codec parameters, e.g. Opus sample rate, H.264 profile.
  • a=candidate / a=fingerprint ICE candidates and DTLS certificate fingerprint — required by WebRTC.
Why "one-way audio" is so common? If the SDP contains an internal address (e.g. 192.168.1.20), the peer will send voice into a black hole. One of the SBC's jobs is to rewrite that address into a publicly reachable one, and optionally relay media. 
v=0
o=1001 3582 3582 IN IP4 192.168.1.20
s=NSBC call
c=IN IP4 192.168.1.20
t=0 0
# Audio: port 40000, RTP/AVP, payload 0 / 8 / 111
m=audio 40000 RTP/AVP 0 8 111
a=rtpmap:0   PCMU/8000
a=rtpmap:8   PCMA/8000
a=rtpmap:111 opus/48000/2
a=fmtp:111 maxplaybackrate=8000;useinbandfec=1
a=ptime:20
a=sendrecv

The c= above is a typical internal address — without an SBC rewrite, the public peer has no way to send media back.

Why SBC

Five hurdles sit between enterprise networks and carriers

SBC (Session Border Controller) is literally a "session border controller". It exists so that two networks that don't trust or understand each other can talk safely.

1. NAT & Address Invisibility

Internal terminals don't know their own public address; SDP contains private IPs; firewalls randomly remap ports. The SBC fixes the path by rewriting SDP, symmetrical RTP and port prediction.

2. Security & Toll Fraud

SIP ports exposed to the public Internet are constantly scanned, brute-forced and registration-hijacked. The SBC does authentication, rate limiting, allow/deny lists and auto-ban — blocking attacks before they reach your business logic.

3. Protocol & Codec Incompatibility

Vendors differ on headers, SDP ordering and session timer behavior. The SBC normalizes protocol and trims capabilities, enabling transcoding when needed so both sides can "understand" each other.

4. Topology Exposure

If your internal PBX talks directly to the outside, peers can see your server addresses, ports and internal numbering plan. B2BUA splits the call into two legs, hiding your internal topology.

5. Billing, Recording & Compliance

Only when media passes through the SBC can packet loss, jitter and MOS be reliably measured, and recording, CDR and auditing be completed. In bypass mode all this data is lost.

What happens without an SBC

  • Calls ring but are silent when answered
  • Internal server addresses get scanned from outside
  • "Signaling works, media doesn't" across vendor gear
  • High international bills after a brute-force breach
  • When things break, you can only inspect half the logs
Summary: An SBC is not an "optional accelerator" — it is the border infrastructure for public SIP deployments. It simultaneously acts as a security gateway, protocol translator, media proxy and observation point.
How It Works

What an SBC actually does inside

Think of an SBC as a pipeline: every incoming INVITE passes through auth, routing, rewriting, media and billing in order.

  1. Signaling Firewall — Validate format and source, rate-limit, reject malformed requests and scans.
  2. Authentication — Confirm identity via Digest challenge, querying HA1 from the registration store when needed.
  3. Routing — Match the dial plan by called number, caller and time-of-day, deciding which extension or trunk to route to.
  4. B2BUA Leg Split — One leg on the caller side, one on the callee side, each maintaining independent transactions and dialogs.
  5. Rewrite & Negotiate — Rewrite R-URI, Via, Contact and SDP; trim codecs; handle NAT.
  6. Media & Billing — Relay or bypass per policy, collect RTP stats, write CDR and stop recording on teardown.

Mapping to NSBC

Signaling and media happen inside the same daemon, so border behavior is configured in one place:

  • security: allow/deny lists, rate limiting, auto-ban
  • registrar / Location DB: registration and addressing
  • dialplan: routing and number rewriting
  • signaling: B2BUA two legs and SDP handling
  • media_bridge: RTP / DTLS-SRTP relay
  • billing / recording: CDR and recording
Media Path

Relay or bypass? Two tradeoffs

SBC can let media pass through itself (relay) or only rewrite signaling and let media flow directly (bypass). Which one you choose depends on whether you need to see the media.

WebRTC

Why browsers need an SBC even more

WebRTC writes security into the protocol: media must be encrypted, addresses must be negotiated via ICE, certificate fingerprints must travel with SDP. Traditional SIP terminals don't have these capabilities.

  • Different transport — Browsers carry SIP over WSS, not UDP 5060.
  • Different media — WebRTC mandates SRTP with keys negotiated by DTLS.
  • Different codecs — Browsers prefer Opus / VP8 / H.264; PSTN usually speaks G.711.
  • Different networking — ICE, STUN and TURN are needed to handle NAT and firewalls.

Here the SBC is not just a "border" — it is a translator: it unwraps WSS back to SIP, converts DTLS-SRTP to plain RTP/SRTP, transcodes on demand, and lets browsers talk to phones and carriers.

Common Misconceptions

A few easy-to-confuse questions

Is an SBC just a firewall?

No. Firewalls allow/deny by IP and port. An SBC understands SIP semantics: it can tell whether a registration is legitimate, where a call should route, and whether addresses inside an SDP need rewriting. They are usually used together.

If I have a PBX, do I still need an SBC?

If the PBX only serves the internal network, maybe not. But the moment you connect to the public Internet, a carrier trunk, or WebRTC, you need an SBC to handle security, NAT and interop. NSBC ships both in the same system, but you can still enable only the border functions you need.

Why does it ring but have no voice?

Signaling working only means the SIP path is fine. Silence usually comes from unreachable SDP addresses, blocked RTP ports, no codec intersection, or a media path that didn't go through a usable relay.

Is SIP always plaintext?

No. SIP can run over TLS (SIPS, default port 5061) and WebRTC uses WSS. Media is encrypted with SRTP or DTLS-SRTP.

Does successful registration mean calls will work?

Not at all. Registration only says the terminal and registrar can reach each other. Actual calls also depend on routing rules, callee online status, media negotiation and firewall allowances.

Is media bypass always better?

Bypass has lower latency and uses fewer resources, but loses media visibility and makes recording or transcoding impossible. For public Internet and WebRTC scenarios, relay is usually the right choice.
