WebRTC 与 SIP 互通

浏览器说的是 WebRTC 语言，话机与运营商说的是 SIP 语言。SBC 站在中间，同时翻译信令、媒体与地址。这一页把转换过程、抓包特征与故障排查讲清楚。

总览

两端不直接对话

WebRTC 与 SIP 并不会"互相兼容"，而是各自与 SBC 建立一段独立会话，由 SBC 负责把两侧拼起来。

差异

三个平面，逐项对齐

平面WebRTC 侧SBC 的处理SIP 侧
信令WSS，子协议 sip还原为 SIP，补 Via / rport / Session-IDUDP / TCP / TLS
会话描述ICE 候选、DTLS 指纹、BUNDLE、rtcp-mux终结 ICE，重写 c= / m=，过滤不适用的属性普通 SDP，静态地址与端口

过程

一次浏览器呼叫话机

从注册到媒体桥接，SBC 一共做了六件事。任何一步缺失，表现都是"能振铃但没声音"。

  1. 注册 — 浏览器通过 WSS 连接 /ws，完成 Digest 注册与保活。
  2. 发起 — 拨号后发送 INVITE，offer 中带 ICE 候选、DTLS 指纹与 Opus。
  3. 鉴权与路由 — SBC 校验身份，查询注册库，命中拨号计划。
  4. 重建 B 腿 — 向话机发起新的 INVITE，SDP 换成话机能理解的地址与编解码。
  5. 应答与握手 — 话机 200 OK 后，SBC 回填 answer，浏览器完成 DTLS 握手。
  6. 媒体中继 — 两段媒体在 SBC 内桥接，同时统计质量并生成 CDR。

WSS 帧与 SIP 报文的关系

# 1) WebSocket 握手（浏览器 → NSBC:5062）
GET /ws HTTP/1.1
Upgrade: websocket
Sec-WebSocket-Protocol: sip

# 2) 握手成功后，每个文本帧装载一条完整 SIP 报文
INVITE sip:1002@nsbc.local SIP/2.0
Via: SIP/2.0/WSS 192.168.1.20;branch=z9hG4bK-1a2b;rport
From: <sip:1001@nsbc.local>;tag=8f3c
To: <sip:1002@nsbc.local>
Call-ID: 5d1e9c7a
CSeq: 1 INVITE
Content-Type: application/sdp

v=0
m=audio 40000 UDP/TLS/RTP/SAVPF 111
a=fingerprint:sha-256 3A:...
a=rtpmap:111 opus/48000/2

WebSocket 的帧边界就是 SIP 报文边界，因此不需要靠 Content-Length 分帧；WSS 上也不允许使用 UDP。

实现要点

四个必须对齐的点

信令：WSS 进，SIP 出

浏览器连接 wss://<host>:5062/ws，子协议固定为 sip。SBC 需要补齐 Via 的 rport、Contact 与 RFC 7989 Session-ID，否则抓包时无法把两段会话对应起来。

媒体：先终结，再决定加密

SBC 在浏览器侧终结 DTLS-SRTP，再以 SRTP 或 RTP 与 SIP 侧通信。只要 B 腿是 WS/WSS，就应视为 WebRTC 并走媒体锚定，否则容易出现"信令通、媒体不通"。

编解码：先取交集，再谈转码

H.264 统一收敛到 Baseline（profile-level-id=42e01f，packetization-mode=1）；Opus 可限制 maxplaybackrate=8000。若对端只有 G.711，需要启用转码模块，否则会以 488 / 415 结束。

连接性：ICE 失败要能恢复

网络切换或 NAT 映射过期时，客户端应调用一次 restartIce() 重新收集候选；服务端保持媒体端口稳定，避免频繁 re-INVITE 造成额外抖动。

最小配置

让互通先跑起来

下面只保留与 WebRTC 接入直接相关的键。证书由 nsbc-web 首次启动时生成，或提前放入 tls/ 目录。

sip:
  ws:
    enabled: true
    port: 5062
    tls: true

media:
  # WebRTC 接入建议锚定媒体，才能看得见 SRTP 与质量
  default_mode: relay
  allow_bypass: false
  # 内网对等测试可临时改为 true
  trust_private: false

修改后执行 nsbc_cli config.reload 或发送 SIGHUP，无需重启进程。

上线前自测清单

  • 浏览器控制台没有 ICE failed，候选包含 srflx
  • 抓包能看到 DTLS ClientHello / ServerHello
  • answer 中的 m= 数量与 offer 一致
  • 双向音频正常，DTMF 按键可被对端识别
  • 切换网络后 30 秒内自动恢复
  • CDR 中编解码字段与预期一致（opus 或转码后 g711）
排障

常见互通故障

先确认是哪一段出了问题：浏览器到 SBC，还是 SBC 到话机。两边分别抓包，通常五分钟内能定位。

现象常见根因处理方向
注册成功，呼叫返回 488 / 415双方编解码无交集（Opus 对 G.711）启用转码，或在 offer 中加入 PCMU
能振铃，接通后无声SDP 地址不可达，或 ICE 未完成开启媒体中继，放行 RTP 端口段
只有单向音频呼入时新建 transceiver，answer 未包含该 m-line复用 offer 已创建的 transceiver 再绑定轨道
ICE failed，媒体中断候选不足，UDP 被防火墙拦截配置 STUN / TURN，客户端重启一次 ICE
DTLS 握手失败证书指纹被中间设备改写，或 SDP 被裁剪检查 a=fingerprint 是否原样透传

WebRTC and SIP Interoperation

Browsers speak WebRTC, phones and carriers speak SIP. The SBC sits in the middle, translating signaling, media and addresses all at once. This page walks through the conversion process, packet-capture characteristics and troubleshooting.

Overview

They don't talk to each other directly

WebRTC and SIP are not "mutually compatible". Instead, each establishes its own independent session with the SBC, and the SBC stitches the two sides together.

The Differences

Three planes, aligned item by item

The Process

A browser calling a phone

From registration to media bridging, the SBC does exactly six things. Miss any one and the symptom is "it rings but has no voice".

  1. Register — The browser connects to /ws over WSS, completes Digest registration and keepalive.
  2. Initiate — Dialing sends an INVITE with ICE candidates, DTLS fingerprint and Opus in the offer.
  3. Auth & Route — SBC verifies identity, queries the registration store and matches the dial plan.
  4. Rebuild B-leg — Originate a new INVITE toward the phone, with SDP rewritten to addresses and codecs the phone understands.
  5. Answer & Handshake — After the phone's 200 OK, SBC fills in the answer and the browser completes its DTLS handshake.
  6. Media Relay — The two media legs are bridged inside the SBC; quality stats are collected and a CDR is generated.

How WSS frames relate to SIP packets

# 1) WebSocket handshake (browser → NSBC:5062)
GET /ws HTTP/1.1
Upgrade: websocket
Sec-WebSocket-Protocol: sip

# 2) After handshake, each text frame carries one complete SIP packet

Via: SIP/2.0/WSS 192.168.1.20;branch=z9hG4bK-1a2b;rport
From: <sip:1001@nsbc.local>;tag=8f3c
To: <sip:1002@nsbc.local>
Call-ID: 5d1e9c7a
CSeq: 1 INVITE
Content-Type: application/sdp

v=0
m=audio 40000 UDP/TLS/RTP/SAVPF 111
a=fingerprint:sha-256 3A:...
a=rtpmap:111 opus/48000/2

WebSocket frame boundaries are SIP packet boundaries, so Content-Length framing is unnecessary. UDP is also not allowed over WSS.

Implementation Keys

Four points that must align

Signaling: WSS in, SIP out

Browsers connect to wss://<host>:5062/ws with a fixed subprotocol of sip. The SBC must fill in rport in Via, Contact and RFC 7989 Session-ID — otherwise you won't be able to correlate the two legs in packet captures.

Media: terminate first, then decide encryption

The SBC terminates DTLS-SRTP on the browser side and then talks to the SIP side with SRTP or RTP. Whenever the B-leg is WS/WSS, treat it as WebRTC and anchor media — otherwise you will see "signaling works, media doesn't".

Codecs: intersect first, transcode second

H.264 always converges to Baseline (profile-level-id=42e01f, packetization-mode=1); Opus can cap maxplaybackrate=8000. If the peer only speaks G.711, enable the transcoder module or the call ends with 488 / 415.

Connectivity: ICE failure must be recoverable

On network switches or NAT-map expiry, the client should call restartIce() to recollect candidates. The server should keep media ports stable to avoid unnecessary re-INVITEs and extra jitter.

Minimal Config

Get interop running first

Only the keys directly related to WebRTC access are shown below. Certificates are generated by nsbc-web on first start, or pre-placed into the tls/ directory.

sip:
  ws:
    enabled: true
    port: 5062
    tls: true

media:
  # WebRTC access should anchor media so SRTP and quality are visible
  default_mode: relay
  allow_bypass: false
  # Can be set to true temporarily for internal peer tests
  trust_private: false

Run nsbc_cli config.reload or send SIGHUP after changes — no process restart needed.

Pre-launch self-check list

  • No ICE failed in the browser console; candidates include srflx
  • Packet captures show DTLS ClientHello / ServerHello
  • Number of m= lines in the answer matches the offer
  • Bidirectional audio is normal; DTMF keys are recognized by the peer
  • Automatic recovery within 30 seconds after network switch
  • Codec field in CDR matches expectation (opus or g711 after transcode)
Troubleshooting

Common interop failures

First figure out which leg is broken: browser ↔ SBC, or SBC ↔ phone. Capture both sides separately — most issues can be localized within five minutes.

SymptomCommon Root CauseDirection to Fix
Registration OK, call returns 488 / 415No codec intersection (Opus vs G.711)Enable transcoding, or add PCMU to the offer
Rings, but silent when answeredUnreachable SDP addresses, or ICE didn't completeEnable media relay, allow the RTP port range
One-way audio onlyInbound creates a new transceiver, answer doesn't include that m-lineReuse the transceiver already created by the offer before binding tracks
ICE failed, media dropsNot enough candidates, UDP blocked by firewallConfigure STUN / TURN, restart ICE once on the client
DTLS handshake failsCertificate fingerprint rewritten by an intermediate device, or SDP trimmedCheck that a=fingerprint is passed through verbatim
Session lingers after hangupWebSocket closed abnormally, no BYE was sentRely on OPTIONS keepalive and timeout cleanup
Mapping to NSBC: WSS listens on 5062/ws; when the B-leg is WS/WSS it automatically picks SRTP relay; the cross-platform SDKs unify transceiver reuse, H.264 Baseline, Opus maxplaybackrate=8000, and restart ICE once on failure. Details in Docs · SIP and Media.
