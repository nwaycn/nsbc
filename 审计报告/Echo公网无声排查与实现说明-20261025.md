# NSBC Echo 公网无声排查与实现说明

日期：2026-10-25  
范围：Dialplan `echo` / originate `&echo`、SIP 应答行为、RTP relay、公网 NAT 排查  
用途：供平台与运维团队排查公网呼叫已接通但 echo 无声音的问题

## 1. 先说结论

1. `100 Trying`、`180 Ringing`、`183 Session Progress`、`200 OK` 是 SIP 信令状态；它们不能单独证明 RTP 已经到达或音频能够双向传输。
2. 当前 `echo` 是**已有 RTP relay 上的环回模式**，不是音频发生器，也不是单腿 IVR。它把每一侧收到的 RTP 发回该侧的对端地址；两侧各自听到自己的回声。
3. Echo 无声时，优先确认呼叫是否有最终 2xx、relay 是否创建、`echo_mode` 是否开启、RTP 是否到达，以及改写后的 SDP 公网 IP/端口是否可达。
4. 公网部署中，尤其要核对 `sip_profile.external_rtp_ip`。源码中 profile 未配置外部 RTP IP 时，SDP 改写会回退到本地媒体 IP。仅配置 SIP 信令的 `sip.extern_ip` 不等于媒体 SDP 已使用公网地址。

## 2. Echo 的实际实现行为

### 2.1 `echo` 不是音频源

Dialplan `echo` app 会查找呼叫已有的 bridge relay，找到后设置环回标记；未找到 relay（例如 relay 尚未创建或呼叫采用 bypass）时会失败。它不会自行创建媒体 relay、播放提示音、自动应答或生成 RTP。

实现位置：

- [app_registry.c](../src/mod/dialplans/app_registry.c)：`app_echo()` 查找 relay，成功后调用 `rtp_relay_set_echo()`。
- [media_bridge.c](../src/media/bridge/media_bridge.c)：`relay_recv_one()` 在 echo 模式下将目的 side 设为收到包的同一 side。
- [b2bua.c](../src/sip/b2bua.c)：originate 的 `&echo` 后置 app 等待 B 腿确认后，再启用 relay echo。

### 2.2 Echo 模式下的 RTP 方向

正常 relay 是 side 0 收到后转发至 side 1，side 1 收到后转发至 side 0。Echo 模式把接收侧作为发送目的侧，因此：

- side 0 收到 RTP → 发回 side 0 对应的公网/本地 peer；
- side 1 收到 RTP → 发回 side 1 对应的 peer。

因此，要听到回声，端点必须先把 RTP 发到 NSBC，NSBC 还必须能将 RTP 发回端点的实际可达地址。仅仅看到 SIP 200 OK 不代表这两步成功。

### 2.3 SIP 响应时序

- 初始 INVITE 到达后，B2BUA 会本地发 `100 Trying`。它表示请求已接收，不代表呼叫已经接通。
- `180/183` 只会在下游返回相应 provisional response 时透传；`183` 可能携带 early-media SDP，但不保证媒体已通。
- 下游 B 腿返回 2xx 后，B2BUA 将经 SDP 处理的最终应答发给 A 腿，通常是 `200 OK`。
- 已接通呼叫上切换 echo 不会重新回答同一个 INVITE，也不会因此再发一次 180/200。

对应逻辑可在 [b2bua.c](../src/sip/b2bua.c) 的 `new_invite`、B 腿 provisional response 与 2xx response 路径中查看。

## 3. 公网无声的高优先级检查项

### 3.1 SIP 是否真正接通

获取一次完整失败呼叫的 SIP trace 或抓包，确认：

- 收到 `100 Trying` 后，是否继续收到 `180/183`；
- 最终是否收到 `200 OK` 或其他 2xx；
- 200 OK 是否对应正确 Call-ID/对话；
- 200 OK 的 ACK 是否成功；
- 如果只有 100/180/183，没有最终 2xx，先排查拨号路由、下游 B 腿和应答流程；此时不应先把问题归为 echo RTP。

TLS/WSS 信令需要使用端点日志、已解密 trace 或服务器侧 SIP trace；普通网络抓包可能无法直接读取响应码和 SDP。

### 3.2 检查 offer/answer SDP 中的媒体地址

至少检查 INVITE offer 和最终 200 OK answer 中的：

- `c=IN IP4 ...` / `c=IN IP6 ...`：媒体连接地址是否为端点/公网可达地址；
- `m=audio <port> ...`：媒体端口是否非零、符合预期；
- codec/PT、`a=rtpmap`、方向属性是否兼容；
- 普通 RTP 与 SRTP/DTLS-SRTP 属性是否匹配；
- 若使用 WebRTC，检查 ICE candidate、DTLS fingerprint、setup 属性与 ICE 连通性。

公网下 `c=` 不应是公网客户端无法路由到的私网/容器地址，也不应是 `0.0.0.0`。端口要与实际 relay 分配相符。

### 3.3 区分 SIP 外网地址与 RTP 外网地址

- `sip.extern_ip` 用于信令侧地址处理/本地 host 推导，不能据此推断 SDP 中的 RTP 地址已经改写。
- 媒体 SDP 路径通过呼叫 profile 的 `external_rtp_ip` 获取公网 RTP IP；若该字段为空，会 fallback 到 media bridge 的 `local_ip`。
- 公网部署需要核对当前呼叫实际使用的 SIP profile、其 `external_rtp_ip` 值，以及最终发给端点的 SDP。不要只看配置文件中的 SIP IP。
- RTP/RTCP 端口范围须在云安全组、主机防火墙及 NAT/端口映射中开放并正确转发。配置样例 RTP 端口范围是 10000–59999，但排障应以当前生效配置为准。

相关代码：[signaling.c](../src/core/signaling.c)、[sip_profile.c](../src/sip/sip_profile.c)、[media_bridge.c](../src/media/bridge/media_bridge.c)。

### 3.4 确认 relay 和 echo 是否真的运行

检查同一 Call-ID/呼叫的日志：

- `echo: RTP loopback ON` 或 `echo_mode 1`：echo 开关已设置；
- relay lookup 失败、`not yet built or bypass mode`：没有可供 echo 使用的 relay；
- `★RECV`：媒体 relay 收到了 RTP/RTCP 包；
- `★ SENDTO`：relay 正尝试把包发回相应 side；
- `sendto FAIL`：本机 UDP 发送调用失败，需看 errno、目标地址和端口；
- `DROP` 相关日志：检查对端 latch、NAT 学习、precondition、SRTP 等丢包原因。

日志中看到 `echo_mode 1` 只能证明状态切换，不等于 RTP 已经到达，也不等于远端实际收到回声包。

## 4. 建议的逐步定位流程

### 第一步：确定呼叫控制面结果

保存完整呼叫 SIP trace，记录 INVITE、所有 1xx、最终响应、ACK、BYE，以及每个 SDP。明确最终是 2xx 还是超时/错误响应。

### 第二步：核对 relay 与 echo 状态

按 Call-ID 对齐 B2BUA、dialplan、media 日志。确认 relay 已创建、不是 bypass，并看到 echo 开启日志。若 relay lookup 失败，先修复 app 执行时机/媒体模式/relay 建立，不要先排查网络包回程。

### 第三步：核对 SDP 地址和端口

将最终 SDP 的媒体 IP/端口与当前 profile 的 `external_rtp_ip`、relay 端口范围及端口映射逐一比对。公网电话无法访问 NSBC 的私网 IP 时，必须确认公网映射确实能转发到公布的媒体端口。

### 第四步：双向抓 RTP

在服务器侧按实际 RTP 范围抓包，例如：

```sh
tcpdump -ni any 'udp portrange 10000-59999'
```

根据部署环境和生效端口调整范围。分别确认：

1. 公网电话的 RTP 是否到达 NSBC；
2. NSBC 是否从 relay socket 发出回声 RTP；
3. 发出的目的地址/端口是否是收到 RTP 的实际公网源地址/端口；
4. 对端是否收到回包。

如果抓包看到入站 RTP、没有出站包，结合 `DROP` 与 `sendto FAIL` 查 relay 状态；如果有出站包但端点收不到，查 NAT、防火墙、云安全组和回程路由；如果服务器没有入站 RTP，优先查 SDP 和媒体端口可达性。

### 第五步：核对端点和 codec/安全协商

若 RTP 到达且已发回，但仍无声，核对包是否为端点实际协商的 RTP/SRTP 格式、codec/PT 是否有效、SRTP 保护状态是否匹配、端点是否把返回媒体送入播放设备。WebRTC 呼叫还需检查 ICE nomination 和 DTLS-SRTP 握手是否完成。

## 5. 结果判读速查

| 观测结果 | 优先排查 |
|---|---|
| 只有 100，没有最终响应 | 路由匹配、B 腿建立、呼叫失败/超时。100 不是接通。 |
| 有 180/183，没有 2xx | 振铃/early media 阶段；检查下游应答和是否有 early-media SDP/RTP。 |
| 有 200 OK，但没有 relay/echo 开启日志 | 呼叫是否真正进入 echo app、relay 是否创建、是否误走 bypass。 |
| 有 echo 开启日志，没有 `★RECV` | SDP 媒体 IP/端口、端口映射、云安全组/防火墙、端点是否发 RTP。 |
| 有 `★RECV`，大量 DROP | 查看 drop 原因、latch 状态、SRTP/DTLS、precondition。 |
| 有 `★RECV`，有 `sendto FAIL` | 查 sendto errno、fd、目标 peer 地址和端口。 |
| 服务端抓到回声出站包，端点没收到 | 查公网 NAT 回程、端口映射、防火墙、路由。 |
| 端点收到包仍无声音 | 查 SDP codec/PT、SRTP/DTLS 状态、端点播放/音频设备。 |

## 6. 源码层需要跟进的事项

### 6.1 `echo_mode` 存在线程数据竞争风险

在 [media_bridge.c](../src/media/bridge/media_bridge.c) 中，`rtp_relay_set_echo()` 写普通 `int echo_mode`，RTP relay 路径同时读取该字段。注释说明写入来自外部模块/线程，而媒体线程读取；普通非原子变量不能在没有同步的情况下跨线程读写。建议优先将 echo 切换投递到 relay 所属 Reactor 执行，或采用满足生命周期和内存序要求的原子状态，并用 ThreadSanitizer/并发测试验证。

这可能导致 echo 切换瞬间状态不一致，但无法解释所有公网无声问题，不应替代 SDP/RTP 抓包排查。

### 6.2 Echo app 的失败应有明确的呼叫行为与指标

当前 `app_echo()` 在 relay 暂不可用或不存在时等待重试后返回失败。平台应确认 dialplan 对 `APP_RC_FAILED` 的后续处理是否符合预期，并考虑为 relay lookup 失败、等待超时、echo 启用/停用增加可按 Call-ID 关联的指标和结构化日志。

### 6.3 观测时避免将日志当作媒体成功证明

`echo_mode 1` 是控制面状态；`★RECV` 是收到包的证据；出站抓包是发出包的证据；端点确认收到包并播放才是完整声音路径。建议诊断面板分别呈现这些状态，不要用一个“echo enabled”标志代表端到端音频正常。

## 7. 平台团队建议采集的最小证据包

每次复现请保留：

1. 脱敏后的完整 SIP trace（含最终响应、ACK、offer/answer SDP）；
2. 呼叫对应的 profile 名称，以及该 profile 生效的 `external_rtp_ip`；
3. 与 Call-ID 对应的 `echo_mode`、relay lookup、RECV、DROP、SENDTO 日志；
4. 同时间窗口的服务器 RTP 双向抓包；
5. 主机防火墙、云安全组和 NAT/端口映射的实际规则；
6. 通话端点类型（普通 SIP、SIP over TLS、WebRTC）、codec、安全模式和公网/运营商网络信息。

分享日志或抓包前应脱敏电话号码、账号、认证头、公网地址及其他敏感信息。

## 8. 总结

先确认最终 2xx 和 SDP，再确认公网 RTP 能到达 relay，最后确认 echo 模式将包发回正确 peer。当前实现的 echo 是**在已有双向 relay 上逐侧回环 RTP**，不是拨入即播放的测试音服务。公网无声时，优先核实 profile 的 `external_rtp_ip`、最终 SDP 中的媒体地址/端口、RTP 端口映射与实际收发抓包；同时修复 `echo_mode` 跨线程普通变量读写的竞争风险。
