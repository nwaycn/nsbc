### R-08 b2bua re-INVITE — ⚠️ 自我修复引入类型错配 bug 已立即修正

**事件时间线**:
1. Round 4 发现 `(void)send_invite_b(...)` 丢弃返回值（返回类型 `sip_txn_t*`）
2. 第一次修复写成 `int rc = send_invite_b(...)` → **严重类型错配**（指针截断为 int）
3. Round 5 审计过程中发现 → 立即修正为正确写法

**第一次修复（错误写法）**:
```c
int rc = send_invite_b(c, ...);           // ← 把指针截断为 int！
if (rc != NSBC_OK) { ... }                // ← 比较 int 和 int 常量，但返回值是指针
```
这会导致 **64 位机器上高 32 位地址被截断**，且 `NSBC_OK`（通常 0）和 NULL 指针都是 0 → 失败时 rc=NULL=0 被误判为"成功"。

**修正后（正确写法，与 b2bua 模块其他 7 处 send_invite_b 调用一致）**:
```c
sip_txn_t *t = send_invite_b(c, 1, other->offer, other->offer_len, 1, NULL);
if (!t) {
    llog(LOG_WARN, "b2bua", "re-INVITE Bob failed call=%p", (void *)c);
}
```

**教训**: C 语言函数返回类型修改后必须全仓 grep 检查调用点类型一致性。**修复 R-08 的过程本身就引入了新 bug**，幸亏在用户编译前被审计 catch。

## 🟠 High 级

### R-11: 自我修复引入类型错配 — `int rc` 接 `sip_txn_t*` 指针（**已修正**）

**位置**: `src/sip/b2bua.c:7148`（修正前）

**问题**: `send_invite_b` 返回 `sip_txn_t *`，第一次修复写成 `int rc = send_invite_b(...)`。

**严重性**: 
- 64 位系统上指针截断为 32 位 int
- NULL 指针（send_invite_b 失败）= 0 = NSBC_OK → **失败路径被完全吞掉**
- 如果有编译 `-Wall -Wconversion` 会警告，但 gcc 默认不开启

**当前状态**: ✅ **已在审计过程中修正**。修正后与 b2bua 模块其他 7 处 send_invite_b 调用保持一致风格：
```c
sip_txn_t *t = send_invite_b(...);
if (!t) { llog(LOG_WARN, ...); }
```

## 修复事故复盘：R-08 自我修复引入类型错配

这轮最有价值的发现不是某个新 bug，而是**修复 R-08 的过程本身就引入了新 bug**。原因链：

```
1. Round 4 发现 (void)send_invite_b 丢弃返回值
2. 修复时假设 send_invite_b 返回 int（看名字像 command 返回码）
3. 没看函数签名直接写 int rc = ...
4. 64 位指针截断为 int，NULL=0=NSBC_OK 导致失败路径继续被吞
5. Round 5 审计新扫维度，查 serde/敏感数据时顺便 grep send_invite_b → 发现签名
6. 立即修正为 sip_txn_t *t = ... + if (!t)
```

**防止再犯的 checklist**（已加入 stability-first SKILL.md P0）:
- ✅ **修复 syscall/函数调用后必须 grep 函数签名确认返回类型**
- ✅ **修复后 grep 其他调用点确认风格一致性**（`send_invite_b` 其他 7 处全是 `*txn = send_invite_b(...)` + `!txn`）
- ✅ **64 位平台上任何 int 接指针都是自动错**，哪怕编译器没警告
