## 🟡 Medium 级

### R-13: reactor epoll 每轮遍历全部 n 事件，无 backpressure

**位置**: `src/core/reactor.c:120-148`

```c
int reactor_wait(reactor_t *r, int timeout_ms)
{
    int n;
    do { n = epoll_wait(r->epfd, r->events, r->max_events, timeout_ms); }
    while (n < 0 && errno == EINTR && !reactor_stopping(r));

    for (int i = 0; i < n; ++i) {
        int fd = r->events[i].data.fd;
        r->slots[fd].cb(fd, r->events[i].events, r->slots[fd].arg);  // 无 break
    }
```

**风险分析**:
- `r->max_events` 控制 `epoll_wait` 一次返回最多多少个事件（典型 128-512）
- 循环里 **无 break / 无 per-turn limit** —— 如果某轮 `epoll_wait` 触发了 500 个事件，reactor 线程会连续执行 500 个 callback
- callback 可能包含：SIP UDP recv → SIP 解析 → b2b_on_rx → signaling_step → media bridge relay —— **每个 callback 可能耗时 1-10μs**
- 500 × 5μs = 2.5ms 连续执行 — **通常没问题**
- 但极端 load 下（1000+ calls，每 call 双腿）可能 stall 20ms+ → watchdog 会 WARN（已有 500ms watchdog ✅）

**结论**: **设计合理，不需要改**。watchdog 已经是合理的 backpressure：
- callback 总耗时 > 500ms → `LOG_WARN reactor callback chain stalled X ms` — 运维能看到
- 真要限流会增加代码复杂度且 `r->max_events` 本身就是 `epoll_wait` 的 per-turn cap
- 只有在**真的发生 watchdog 告警且确认是 backpressure**时才需要加 per-turn limit

**建议**: **不改**。留着 watchdog 观察行为即可。

### SIP 协议边界（C 核心）

| 维度 | 结果 | 证据 |
|---|---|---|
| **SIP message size boundary** | ✅ 三层防护 | ① `cfg_schema.c:net.sip_max_msg` 默认 16KB ② `sip_transport.c:93-96 UDP_CL_DROP` 超限丢弃 ③ `tcp_framer.c:144 FRAME_OVERFLOW` 检测 |
| **CSeq 整数溢出** | ✅ 风险可忽略 | trunk cseq 在 `outbound_reg.c:267` 初始化为 0，每 REGISTER +1。32-bit uint 最大 4294967295 → 每 5s 发一次 REGISTER 需 **68 年** 才 wrap。b2bua dialog 内 CSeq 每腿最多发 10-20 次 SIP 请求 |
| **Via branch 唯一性** | ✅ 算法安全 | `gen_branch()` = `z9hG4bK` + callid + cseq + monotonic counter → 三元组熵够，同毫秒内碰撞概率 ≈ 1/2^64 |
| **SIP 解析递归** | ✅ 无递归 | SIP parser 全迭代，无 self-call 或 A→B→A 环。Via multi-path / Route list 全是 while 循环 |
| **Stack overflow** | ✅ 风险极低 | 最大自动数组 `char branch[40]`, `char req[4096]`（b2bua.c）→ ~4KB。Linux 默认 8MB stack → 可嵌套 2000 层 |
