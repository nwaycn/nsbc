### L-00: Rust 生产代码 `unwrap()` / `.expect()` — 分类重审后仅 2 处值得改（已修复）

**原评级**: 🔴 Critical → 重审后降级为 🔵 Low

**分类结论**: 全 `web/src/` 共 100 处 unwrap，按性质拆分：

| 类别 | 数量 | 处理方式 |
|---|---|---|
| `#[cfg(test)]` 测试块内 | ~55 | ❌ 保留。测试里 unwrap 是惯例，断言失败本来就该 panic |
| 初始化路径（getrandom、argon2 Params、hash_password） | ~5 | ❌ 保留。系统 RNG 不可用 / argon2 参数构造失败 = 启动级致命错误，panic 是合理的 fail-fast |
| 类型系统已保证（`b.body(body)`、`URL_SAFE_NO_PAD.encode`、`or_insert_with` 后 `get_mut`） | ~7 | ❌ 保留。编译器已保证不会错 |
| `Mutex.lock().unwrap()` poison 处理 | ~25 | ❌ 保留但已知。poison 意味着"另一个线程 panic 后互斥锁还没释放"——当前进程马上崩溃，改 `unwrap_or_else(\|e\| e.into_inner())` 无实质收益。如果要彻底改需要全局架构调整（去掉 Mutex） |
| **请求热路径**（下面两处） | **2** | ✅ **已修复** |

| 文件 | 原行号 | 问题 | 修复 |
|---|---|---|---|
| `coreclient.rs` | 1414 | `strip_prefix("ERR").unwrap()` — if 分支判断 starts_with("ERR") 后理论上安全，但 nsbcd 异常输出 `ERR` 开头但无内容的行仍可能 panic | → `.unwrap_or(line).trim()` |
| `coreclient.rs` | 1717 | `legs.get_mut(&n).unwrap()` — 上一行 `or_insert_with` 已保证 entry 存在，再 get_mut 冗余 | → 直接用 `or_insert_with` 返回的 `&mut LegDump`，省掉二次查找 |

| 文件 | 行号 | 内容 | 频率 |
|---|---|---|---|
| `src/sip/b2bua.c` | 5365 | `llog(LOG_INFO, "b2b", "---- rx REQ ...")` | 每 SIP 请求 |
| `src/sip/b2bua.c` | 5377 | `llog(LOG_INFO, "b2b", "----- rx RESP ...")` | 每 SIP 响应 |
| `src/media/bridge/media_bridge.c` | 417 | `llog(LOG_INFO, "relay", ...)` | 媒体包 hot-path |
| `src/media/bridge/media_bridge.c` | 913 | `llog(LOG_INFO, "relay", ...)` | 媒体包 hot-path |
| `src/media/bridge/media_bridge.c` | 1064 | `llog(LOG_INFO, "relay", ...)` | 媒体包 hot-path |
| `src/media/bridge/media_bridge.c` | 2211–2582 | relay_start 16 条 LOG_INFO | per-call 一次性（可接受） |

**✅ 已修复**: b2bua.c 5 处 LOG_INFO → LOG_DEBUG（rx REQ/rx RESP/txn_srv_input + REQ_DUMP/RESP_DUMP）；media_bridge.c 417/1064 门槛诊断 → LOG_NOTICE、913 transcode → LOG_DEBUG；signaling.c 1 处 → LOG_DEBUG。保留 relay_start 16 条 per-call 一次性 LOG_INFO 不动。

**位置**: `web/src/db/mod.rs` 中所有 Create/Update 结构体

**证据**: 全项目只有 `web/src/routes/auth.rs` 4 处用了 `#[serde(deny_unknown_fields)]`（REQ-WEB-009 明确要求）。但这些对外路由的请求体结构体**全部缺失**:

|---|---|---|

## 🟡 Medium 级

### M-01: `tokio::spawn` 14 处任务句柄未统一追踪

**位置**: `sync.rs:337,369,398`, `uds_server.rs:64,71,85`, `main.rs:583,612`, `tls.rs:97,479`, `ai_agent.rs:42`, `poller.rs:31`

**风险**:
- `sync.rs:369` 的 periodic push 虽然 `let h = tokio::spawn(...)` 存了句柄，但没 `.await` 也没 `abort()`，任务异常退出后只能靠 tokio 日志发现
- `main.rs` 两处 spawn 后完全丢失句柄，如果任务 panic 或 hang 无法 graceful shutdown
- 没有统一的 task registry 或 `JoinHandle` 收集，无法在 SIGTERM 时做 `.abort()` 清理

**建议**: 引入 `ShutdownHandle` 或 `Arc<Vec<JoinHandle<()>>>` 统一追踪 spawn 任务，在 graceful shutdown 时 `.abort()` 所有任务。

### M-02: `std::fs` 阻塞 I/O 在 tokio 异步路径上

**位置**:
| 文件 | 说明 |
|---|---|
| `web/src/tls.rs` | 多处 `std::fs::read/write/create_dir_all`（证书管理） |
| `web/src/main.rs:95,349,408,412` | `std::fs::create_dir_all`, `OpenOptions::open`（日志轮转） |
| `web/src/db/mod.rs:116,131,139,148` | `std::fs::*`（UDS 日志配置目录创建） |
| `web/src/config.rs:205,230` | `std::fs::read_to_string`, `canonicalize` |
| `web/src/auth/audit.rs` | `std::fs::read_to_string`, `OpenOptions::new()` |

**风险**: tokio 默认多线程 runtime 下，`std::fs` 会阻塞整个 worker pool 线程。如果恰好在 tokio 事件循环线程上执行，可能延迟其他异步任务调度。

**建议**: 改用 `tokio::fs::*` 或 `tokio::task::spawn_blocking` 包装。证书管理这些低频路径可以先不动，但审计日志写文件和配置读取这些请求热路径上的应该改。

### M-03: Mutex `lock()` 在同步代码中大量使用

**位置**: `coreclient.rs` ~30 处 `self.calls.lock().unwrap()`，`sessions.rs` 8 处，`limiter.rs` 5 处

**风险**: 虽然当前都在同步代码块里，但 `unwrap()` 在 Mutex poison 时会 panic。更重要的是，**跨 spawn 边界持有 Mutex 会导致 deadlock**——虽然当前代码没看到这个问题，但如果以后有人在持有 Mutex 后加了 `.await`，直接死锁。

**建议**: 全局搜索 `Mutex::new` + 锁持有边界，标记哪些可能跨越 `.await`。所有生产代码 `lock().unwrap()` → `lock().unwrap_or_else(|e| e.into_inner())` 或 `if let Ok(g) = lock()`。

## 🔵 Low 级

### L-01: reactor.c 慢路径日志 `fprintf(stderr, ...)`

**位置**: `src/core/reactor.c` 主循环，单批次 callback 耗时 >500ms 时 `fprintf(stderr, ...)`

**风险**: reactor callback 本身就是 event loop 的热路径，虽然触发条件是慢 callback 已经有问题，但 fprintf 本身是同步 I/O，可能延长 stall。

**建议**: 这个 fprintf 改成 `llog(LOG_WARN, "reactor", "callback stall: %ldms")`，统一走项目日志系统。

### L-02: CRLF/缩进等纯格式改动混入功能 commit

**背景**: 上次 commit `3d5a001` 包含 74 files changed，但 `-w` diff 过滤后仍有 300+ files 是纯行尾变化。review 时噪音淹没真正的改动。

**建议**: 下次 commit 前用 `git add -w` 跳过空白，或配置 `.gitattributes` 统一 `* text=auto eol=lf`，一劳永逸。
