- **sip_transport N 个 SO_REUSEPORT UDP socket**：多 reactor 时循环 N 次 net_udp_open + reactor_add，

- **media_bridge rtp_relay 按端口 hash 路由 + reactor_call 批量提交**：hash_key=rtp_port[0] + rtp_port[1]*31
  → reactor_mgr_route → reactor_call 一次性提交 4 个 reactor_add/del。
  **修复了 stop() 从业务线程 free relay 而 relay_cb 还在跑的 race**（del + callback/fd close 在同一 reactor owner 线程串行化）。
- **main.c shutdown 顺序修复**（Advisor 验证关键 bug）：join 必须在 modmgr_stop_all + drain 之后——
  之前错误地在 modmgr_stop_all 之前 join → reactor 被 free 后 rtp_relay_stop 触达已释放内存 → use-after-free。
- **slot table race 防护**：所有 reactor 对象预创建（main 线程 owner），所有模块 init 的 reactor_add
  在 start_threads 之前完成——slot_ensure 的 realloc 无并发竞争。

### Timer callback 多 reactor 设计结论（零代码改动）

**决策**：timer callback 保持 ticker 线程直接执行，不通过 reactor_call 路由。

**原因**（全量 Grep 验证 59 处 tw_add/tw_mod/tw_del 调用点，7 个模块）：
- SIP txn 重传：`sendto()` UDP（线程安全）
- session timer refresh/expire：改 b2bua 内部状态（worker 线程）
- outbound_reg：改注册状态（worker 线程）
- dialplan sleep：resume dialplan（worker 线程）
- playback：pull RTP（media 线程）
- sweep：清理过期注册

**零 callback 涉及 reactor-owned FD state 操作** → 零 reactor affinity 需求。
timer_wheel.h/.c 零改动，保持 ticker 线程天然串行推 + 执行 callback。

**未来 opt-in 模式**：若出现 media/DTLS timeout 关 reactor-owned FD 的 callback，
callback 在内部自行 `reactor_call(target, fn, arg)` 即可，不修改 timer_wheel 核心。
ticker 线程同步等待短暂阻塞可接受（此类 timeout 频率低），shutdown 期间 reactor_call
返回 NSBC_SHUTDOWN → callback 静默跳过（正确行为）。

### P3 Worker 按需动态扩缩（本轮核心完成）

**改动文件**：`worker.{h,c}`、`main.c`、`cfg_schema.c`、`t_worker_lifecycle.c`

**核心约束**（不可协商——经 Advisor 3 轮 race condition 修复后确认）：
- `worker_t` 数组预分配 `max_workers` 槽位，**永不 realloc**（submitter 无锁读 atomic n_active，realloc = use-after-free）
- scale-up 部分失败必须 rollback（draining + drain queue + pthread_join + 清理 slot 资源）
- resize / destroy / scale-up / scale-down / rollback **全路径持有 resize_lock**
- wpool_destroy：先 `pthread_mutex_unlock` 再 `pthread_mutex_destroy`（POSIX 约束）
- worker_main 退出路径 **只做 thread-local mem_rcu_thread_leave**，不改 pool 共享状态
  （全部共享字段修改移到持有 resize_lock 的 resize/destroy 路径）

**API**：
```c
int wpool_create(pool_out, min_workers, max_workers, queue_cap, rcu);
int wpool_resize(pool, new_n);                    // 幂等
unsigned wpool_max_size(pool);
```

**配置**：
| 键 | 类型 | 标志 | 默认 | 范围 |
|---|---|---|---|---|
| `core.workers` | INT | **HOT** | 1 | [0=按CPU, 64] |
| `core.workers_max` | INT | RESTART | 64 | [1, 64] |

**触发机制**：ticker_main ~1s 周期检查 `core.workers` 配置变化 → `wpool_resize(target)`。
`ctx_stopping` 期间跳过（shutdown 安全）。

**所有权模型**：
| 路径 | 共享字段操作 | 锁 |
|---|---|---|
| submit/any | atomic_load(n_active) 算 idx | 无锁（RELAXED） |
| worker_main 退出 | 只 RCU leave（thread-local） | 无 |
| resize scale-up/down/rollback | slot init / draining / join / 清理 | resize_lock |
| wpool_destroy | lock → close gate → running=0 → sem_post → join 所有 → 清理所有 → unlock → destroy → free | resize_lock |

**关键修复的 4 个 race condition**：
1. worker_slot_init 失败不应调 wpool_destroy（只清自己 slot）
2. scale-up 部分失败已启动 worker 泄漏 → rollback join+清理
3. wpool_destroy 与 ticker resize 并发 → 持 resize_lock
4. worker_main 退出无锁改 pool 共享字段 → **全部移除**

## 1. 结论摘要

建议把 NSBC 演进为**多 Reactor、状态分片、按需 Worker**的架构，但应分阶段推进，不建议直接把现有回调并发执行，也不建议仅增加 Worker 数量。

当前核心主循环创建并运行一个 `ctx.re`，网络及媒体 FD 注册到该 Reactor。配置虽允许按 CPU 数创建 Worker，当前确认 billing CDR flush 使用 `wpool_submit_any()` 提交持久化任务；这不代表 SIP 热路径已并行化。`net.reuseport=true` 也不会单独创建额外 Reactor 或接收线程。

建议目标模型：

1. **Reactor 负责 I/O 和所属状态的串行推进**：一个 Reactor 管理一组 FD、事件回调、连接与定时任务。
2. **会话状态固定归属**：同一 SIP 事务/对话、TCP/TLS 连接、RTP relay 的可变状态由一个确定的 Reactor 所有。
3. **跨 Reactor 通信显式化**：通过有界 mailbox/队列发送命令，不让多个 Reactor 无约束地同时写同一状态对象。
4. **Worker 只处理明确适合异步化的工作**：使用有界队列、背压和可观测的等待时间；不把短小 SIP 状态机工作无差别地移出 Reactor。
5. **先测量，再增加并行度**：保留单 Reactor 回退模式，以 1/2/4 Reactor 和不同 Worker 配置做可复现的对比测试。

## 2. 源码现状与已确认的性能热点

### 2.1 当前线程模型

- [main.c](../src/core/main.c) 创建一个 `ctx.re`，主循环调用 `reactor_wait(ctx.re, timeout)`。
- [reactor.h](../src/include/reactor.h) 的接口描述了“一线程一个 Reactor”的模型，但主程序当前只实例化一个。
- [sip_transport.c](../src/sip/sip_transport.c) 和 [media_bridge.c](../src/media/bridge/media_bridge.c) 将 SIP 与 RTP/RTCP FD 注册到传入的 Reactor。
- `core.workers` 默认按在线 CPU 数创建 Worker；目前确认 billing CDR flush 通过
  `wpool_submit_any()` 提交持久化任务。尚未发现 SIP 状态机工作提交到 Worker；
  因此不能把 Worker 数量视为 SIP 热路径并行度。Worker shutdown 会拒绝新提交并
  drain 已接受工作；销毁池前仍须确保生产者线程已停止并 join。
- [worker.c](../src/core/worker.c) 的空闲线程通过每 worker semaphore 阻塞等待，不再轮询队列；Worker 线程数仍应按实际异步负载配置，不能等同 SIP 状态机并行度。
- `net.reuseport` 配置为 true，但多 Reactor 接收需要多个实际创建并注册的 socket/epoll 实例；单独启用该选项并不构成多 Reactor 架构。

### 2.2 已确认的 C 核心热点

1. **注册更新对分片链表多次线性扫描，并在锁内完成**  
   [location_db.c](../src/registrar/location_db.c)：`loc_upsert()` 先扫描并清理分片过期项，再扫描 AoR 联系人；达到上限时淘汰还会再扫描。注册更新成本随分片节点数增长，并延长同分片锁持有时间。

2. **SIP 事务分片内仍然线性查找**  
   [sip_txn.c](../src/sip/sip_txn.c)：`find_locked()` 遍历分片链表；请求/响应查找在持分片锁时执行。分片只减少每条链表的平均长度，没有消除线性查找。

3. **SIP 对话分片内仍然线性查找**  
   [sip_dialog.c](../src/sip/sip_dialog.c)：`find_obj()` 与 `find_uac_early()` 在锁内逐项扫描分片链表。容量增大或热点分布偏斜时，查找时间和锁占用会随链表长度增加。

4. **RTP 包路径每包竞争共享录音/AI hook 锁**  
   [media_bridge.c](../src/media/bridge/media_bridge.c)：每个带 payload 的 RTP 包都会取得 `rec_hook_lock` 并复制 hook 列表，即使列表为空也需要走锁路径。高包速、多媒体线程下可能成为共享锁热点。

5. **事件序号使用全局共享原子变量**  
   [event_bus.c](../src/core/event_bus.c)：事件写入和 handler 触发都会递增同一全局序号。事件吞吐高时，跨核缓存行争用可能限制扩展性。只有确实要求跨核严格总序时才应保留全局序号。

### 2.3 已确认的 Web CDR 查询热点

1. **恶意标记过滤在应用层扫描大量 CDR**  
   [web/src/db/mod.rs](../web/src/db/mod.rs)：恶意标记查询最多取回并解析 100,000 行，再在 Rust 中过滤和分页；这使查询成本随扫描量增长，并可能漏掉超出上限的匹配记录。应将过滤、计数和分页下推至 SQL，避免静默截断。

2. **前置通配符搜索不利于普通 B-tree 索引**  
   Caller、callee、Call-ID 使用 `LIKE '%value%'` 时，普通 B-tree 通常无法有效定位匹配项。应先确认产品是否必须支持任意子串；可接受时改精确/前缀匹配，否则使用适用于目标数据库的专用索引，并检查实际查询计划。

## 3. 多 Reactor / Worker 的建议判断

### 推荐：有条件地采用多 Reactor

单 Reactor 是易于维护、状态顺序清晰的起点；当它成为 CPU 热点时，会限制单进程吞吐，尤其是 SIP 解析、媒体收发和定时器回调都集中在同一事件循环的情况下。多 Reactor 能将 I/O 回调分散到多个核，但前提是工作和状态也能够有效分片。

多 Reactor **不会自动解决**上节的线性扫描和共享锁问题。若所有 Reactor 仍竞争同一全局表/锁，线程数增加可能只增加锁竞争、缓存一致性流量和尾延迟。RTP 包若跨 Reactor 转发，还可能新增队列/线程间拷贝，使性能低于单 Reactor。

### Worker：不要默认按 CPU 数无条件启动

Worker 适用于可独立处理、允许排队的 CPU 密集或阻塞任务。短小、必须保持顺序的 SIP 事务状态机通常应留在其所有者 Reactor 上。平台应先确认 Worker 的实际业务调用和队列负载，再确定线程数；空闲 Worker 宜通过条件变量、信号量或 eventfd 睡眠，而不是持续轮询。若短期不使用 Worker，应考虑默认禁用或减少线程数，避免无效启动 CPU 数量级线程。

### 建议目标架构

- 配置独立的 `core.reactors`，默认值保持 `1`，允许逐步扩容；最大值受进程 CPU 配额、FD 预算和内存预算约束，而不是只看宿主机逻辑 CPU 数。
- 每个 Reactor 拥有独立 `epoll`、事件批次缓冲和控制唤醒 FD；监听 socket 和已接入连接须有明确的 Reactor 所有者。
- UDP 可为每个 Reactor 创建绑定同一地址/端口的 `SO_REUSEPORT` socket，并各自注册到其 epoll。需验证内核分流行为和流量均衡；不能假定它按 SIP Call-ID 分流。
- TCP/TLS 连接从 accept 起固定归属一个 Reactor；TLS 使用非阻塞状态机。连接上的读写、关闭、超时必须在所有者 Reactor 上串行完成。
- SIP 报文先完成必要的轻量解析，再以事务/对话键选择状态所有者；非所有者 Reactor 通过有界 mailbox 转发，确保重传、响应、CANCEL/ACK 和目标状态由同一所有者串行处理。需要单独处理解析前无法获得键、键缺失或异常报文的路径。
- RTP/RTCP relay 的 FD 与状态固定归属一个 Reactor；建立/拆除 relay 通过命令投递给所有者。尽可能避免每包跨 Reactor 转发。
- 定时器回调必须在被保护状态的所有者线程执行。将当前时间轮/定时器线程的职责明确化，不能让多个 Reactor 并发推进同一个非线程安全时间轮。
- signal、管理 socket、metrics、control socket 应明确归属一个 Reactor，或以线程安全方式接受请求后转发；停止/新增任务必须能唤醒阻塞中的 epoll。
- Worker 采用独立配置、队列上限、队列等待时间指标与显式过载策略。队列满时在 SIP、媒体、后台任务中分别定义可观察的丢弃/拒绝/降级行为，不能静默丢失。

- 固定硬件/虚拟机规格、CPU 配额、内核版本、网卡队列、编译选项和配置；记录测试工具及版本。
- 记录 Reactor CPU 使用率、事件批次大小、单次 callback/批次耗时分布、epoll 唤醒率、定时器延迟。
- 记录 SIP CPS、并发事务/对话/注册数、UDP/TCP/TLS 比例、错误响应/重传、丢包。
- 记录 RTP 双向包率、媒体并发数、录音/AI hook 开关、包处理 p50/p95/p99 延迟。
- 记录 Worker 活跃/空闲数、队列深度、队列等待 p95/p99、拒绝数；分辨“已创建”与“真正承载任务”。
- 对注册、事务、对话表测量分片长度分布、锁等待/持锁时间；对 Web CDR 记录行数、查询计划、数据库耗时与返回行数。
- 测试至少包含纯 SIP、纯 RTP、混合呼叫、注册刷新突发、TLS 建连、超时/重传、长时间稳定运行和过载恢复。

### 阶段 1：先修可独立验证的数据结构和热路径热点

1. 注册表：已建立 AoR 哈希目录，过期清理由周期全表 sweep 承担；upsert 仅清理目标 AoR，并在联系人上限替换时复用淘汰节点。仍需在 Linux 上跑专项测试，并为锁等待/分片分布及更新吞吐建立基准。
2. SIP 事务：当前实现已按 branch/method/kind 使用分片内哈希桶；输入、创建、响应及摘表路径复用单次哈希完成 shard/bucket 选择。仍需 Linux 回归覆盖事务创建、重传、响应、ACK/CANCEL 和超时，并建立查找/碰撞分布基准。
3. SIP 对话：按 Call-ID、local tag、remote tag 建索引；保留 EARLY 匹配语义，并设计并发删除/引用保护。
4. RTP hook：使用不可变快照/原子发布或读侧无锁机制；注册/卸载 hook 时采用安全回收策略，避免 hook 函数指针释放后仍被包路径使用。
5. Event bus：先确认消费者是否依赖严格全局序号；无全序需求时改为每核序号或分段分配，并验证去重、排序和持久化语义。
6. Web CDR：把恶意标记过滤/计数/分页放进 SQL；按实际过滤条件和数据库后端增加或调整索引；对任意子串查询选择并验证合适策略。
7. Worker：若确有异步任务调用，消除空闲忙轮询，记录队列指标；若没有业务负载，避免默认创建无用的 CPU 数量级 Worker。空闲 semaphore、提交/关闭同步及指标源销毁生命周期已实现；Worker 单测现覆盖有界队列过载拒绝、关闭和已接受任务 drain，仍需在 Linux 上执行。

阶段 1 的每项优化应有单项微基准或专项压力用例，防止只凭代码结构推测收益。

### 阶段 2：抽象 Reactor 集合但先以单实例运行

- **当前进展**：已加入单 Reactor 的有界同步 mailbox、eventfd 唤醒、owner 执行和
  stop/drain 基础；`reactor_destroy()` 现在限定 owner 线程调用并返回明确状态，在
  event loop 活跃或命令仍排队时拒绝销毁；正常停机检查 drain/destroy 结果并在失败时
  以非零状态退出；尚未形成 manager/数组，也未将业务调用迁移到 mailbox。
- 将 `ctx.re` 扩展为 Reactor manager/数组，提供创建、启动、停止、注册和归属 API；适配 SIP transport、媒体桥、WS/WSS、OAM FD 和信号处理等所有调用方。
- 先以 `core.reactors=1` 验证行为等价，避免同时引入并行性和接口迁移造成问题。
- 引入有界跨 Reactor mailbox、任务所有者字段、控制唤醒 FD、优雅停止/队列 drain 机制。
- 在调试构建中增加线程归属断言，尽早发现错误 Reactor 操作；为关键状态记录 owner id。
- 确保日志、指标、时间轮、RCU reader、资源销毁和 reload 生命周期与多 Reactor 模型一致。

### 阶段 3：逐步启用 2、4 个 Reactor 并验证亲和性

- 首先从 SIP UDP 开始，使用每 Reactor `SO_REUSEPORT` socket；对比内核接收分布和 SIP 状态分发是否均匀。
- 再迁移 TCP/TLS accept 与连接所有权，然后迁移 RTP/RTCP FD；一次只启用一个协议面，便于定位回归。
- 增加同一 Call-ID/事务在不同网络源端口、NAT 重绑定、重传、CANCEL/ACK、双向代理和超时情况下的跨核测试。
- 每次按 1 → 2 → 4 Reactor 扩容，保留 `1` 作为立即回退选项；暂不自动依据负载动态改变 Reactor 数，避免状态迁移复杂度。
- Worker 按任务类型和测量结果单独启用，不要和 Reactor 数量一同放大到 CPU 数的平方。

### 阶段 4：按剖析结果决定是否进一步并行化

- 使用采样剖析器识别 CPU 热点、锁等待、内存分配、缓存未命中和系统调用成本。
- 只有当 Reactor 仍因明确的长 CPU 工作饱和时，才将该工作拆成 Worker 任务；状态提交仍回到对象所有者 Reactor。
- 对 TLS、编解码、转码、录音、AI/VAD 等工作分别测量并评估专用线程池，避免将不同延迟特性的任务放进同一队列。
- 若性能受网卡、单队列、虚拟机 CPU 配额、数据库或远端依赖限制，应先处理真实瓶颈，而非继续增加线程。

## 5. 压测验收与发布门槛

以下为建议门槛，最终数值应由平台根据目标设备和 SLA 确认。所有对比使用同一测试环境、同一流量模型，至少重复三轮并报告中位数与波动范围。

| 类别 | 建议验收要求 |
|---|---|
| 正确性 | SIP 事务/对话、重传、CANCEL/ACK、注册刷新、TCP/TLS 生命周期、RTP/RTCP、优雅停机及 reload 回归通过；无数据竞争、死锁、崩溃和资源泄漏。 |
| 扩展性 | 2 Reactor 对比 1 Reactor，吞吐应有明确提升；建议目标至少达到 1.6 倍，4 Reactor 建议目标至少达到 2.8 倍。未达到时先分析锁、分流、跨核转发和硬件限制，不默认继续扩容。 |
| 延迟 | 在目标吞吐和过载边界下，SIP/RTP p99 延迟不得超过既定 SLA；相较单 Reactor 基线的 p99 不应回退超过 10%，除非经平台批准。 |
| 丢包/错误 | SIP/RTP 丢包、5xx/拒绝率、队列拒绝数不能因增加并发而恶化；所有限流和队列满行为均需有指标和日志。 |
| 资源 | 报告每核 CPU、总 CPU、RSS、线程数、FD 数、上下文切换、锁等待和队列深度；不得以超额线程或无界内存换取短时吞吐。 |
| 稳定性 | 目标峰值持续压测至少 24 小时，并执行突发、过载、恢复及优雅停机测试；无持续增长的队列、内存或计时漂移。 |
| 回退 | 通过配置可以回到单 Reactor；回退后状态清理、安全停机和端口绑定正确。不得依赖重新构建才能降级。 |

性能报告至少提供吞吐、p50/p95/p99/p99.9 延迟、丢包、CPU、RSS、锁等待、事件批次、队列深度和样本规模，避免只报告最大 CPS 或平均延迟。

## 6. 主要风险与防护

- **线程归属不清**：定义每类对象的 owner，检查所有写路径；跨线程操作经 mailbox 串行化。
- **SIP 报文顺序变化**：以事务/对话键维持亲和；验证异常分流、重传和源地址改变情形。
- **共享锁抵消并行收益**：跟踪每个热点锁的争用和持有时间；优先拆分状态或转为只读快照。
- **定时器竞争与回调执行上下文改变**：规定定时器所属 Reactor 与回调线程，测试超时精度及停机顺序。
- **跨 Reactor 转发增加拷贝和延迟**：尽量在接收时归属正确 owner；测量 mailbox 的字节数、等待时间及拒绝数。
- **`SO_REUSEPORT` 流量偏斜**：按实际内核/网卡/协议测试分布；不能把“启用选项”当成负载均衡验收。
- **Worker 队列过载或语义丢失**：有界队列、任务类型对应的背压策略、可观测拒绝率；禁止静默丢任务。
- **错误的扩容依据**：同时观察 CPU 配额、网卡和外部服务；单 Reactor CPU 未饱和时，多 Reactor 未必有收益。
- **兼容性及迁移风险**：先完成 `core.reactors=1` 的接口迁移，再灰度启用多实例，准备快速回退配置。

## 7. 建议平台团队的首批任务拆分

1. **性能基线任务**：建立 SIP/RTP/注册/CDR 四类可重复基准和统一指标仪表盘。
2. **并发模型盘点任务**：列出所有 Reactor FD 注册点、状态写入方、定时器回调线程和 Worker 实际调用点。
3. **状态索引任务**：分别改造注册表、SIP transaction、dialog 的链表查找，并提供微基准。
4. **媒体热路径任务**：优化录音/AI hook 读路径，验证卸载安全与 RTP 包速率提升。
5. **Web CDR 任务**：实现 SQL 过滤/分页和后端索引，验证查询计划及大表性能。
6. **Reactor manager 任务**：抽象多 Reactor 生命周期，先以单 Reactor 配置跑通全量回归。
7. **多 Reactor 灰度任务**：以 2 个 Reactor 验证 UDP、TCP/TLS、RTP 所有权及扩展性，再决定是否扩大。

## 8. 最终建议

优先顺序建议为：**测量基线 → 修正确定的线性扫描/锁热点 → 盘点并校正 Worker 使用 → 抽象多 Reactor 并以单 Reactor 验证 → 小规模多 Reactor 灰度 → 根据剖析结果进一步并行化。**

这样能避免“线程数增加但吞吐不升、尾延迟变差”的常见结果，并让平台团队把每项结构改造对应到可重复的性能证据和回退方案。
